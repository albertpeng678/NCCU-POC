# Q&A 設計：留 2.5-flash — JSON 三層強化 + 平滑串流打字機

> 設計日期：2026-06-05（Session 5，承接同日 3.5 探索後的轉向）
> 範圍：**僅 `/qa` 問答**。不動 `/recommend`。3.5 路線（response_schema/replay/thinking）保留在 `QA_MODE` 後當未來選項，非預設。

## 一、問題與動機

**症狀**：問答串流回應會把 JSON schema（`{"answer":...}` / ```json 鷹架）外洩到畫面；且 Gemini 串流是「一坨一坨」吐 chunk（時而 5 字、時而 80 字），直接渲染導致畫面跳動、突兀；列課程時表格有時以 raw markdown（`| 課程 | 系所 |`）爬出來。

**為何留 2.5 而非換 3.5（同日探索結論）**：
- 3.5-flash 雖能原生 `response_schema`（從源頭免解析），但實測**目前 high-demand 503 嚴重**，首 token 與總延遲變異大（13s～39s），SDK 重試把延遲拉長；而 **production 跑 2.5 穩定快**。
- 結論：PoC 階段最務實 = **留 2.5（穩、快）+ 用解析/前端手段把「漏 JSON、不平滑、表格 raw」三個問題壓掉**。3.5 待其 503 緩解後再評估（成果已 stash/保留於 `QA_MODE`）。

## 二、架構總覽與資料流

```
使用者問題 → 前端 askQuestion()（EventSource GET /qa/stream，QA_MODE=stream）
  → 後端 stream_answer（2.5 + file_search 串流）：
      逐 chunk 取乾淨 answer prose（強化：JSON-first 也不漏鷹架）→ yield token
      done：parse_qa_response（強化：json_repair + 絕不漏鷹架）→ finalize_qa_answer
  → 前端 token：餵進 createTypewriter（定速緩衝）→ 每 tick 渲染 healed markdown
      （safeMarkdownPrefix + stripInProgressTable → 表格 snap-in、不露 raw |）
  → done：用權威 answer 收尾（防幻覺覆寫）+ citations/followups
```

**核心三招**：(A) 後端 JSON 三層強化（不漏）、(B) 前端定速緩衝（平滑）+ healed markdown（表格不 raw）、(C) `QA_MODE` 保留 3.5 回退。大量**重用本分支已建好的零件**。

## 三、Part A — JSON 三層強化（後端 `backend/qa.py`）

2.5 掛 file_search **不能用 response_schema**，只能從自由文字解析。現行 `_PROMPT_TEMPLATE` 要求模型「先寫 prose+表格 markdown，再附一段 ```json{answer,followups}```」。漏點：(a) 模型偶爾 **JSON-first**（沒寫 prose 直接吐 JSON）→ 串流端 `find("```")==-1` 會把 raw JSON 當 prose 串出去；(b) `parse_qa_response` 解析失敗時 fallback **回傳含鷹架原文**。

**A1 — `parse_qa_response` 強化（done 時解析）**
維持現有 fence/brace 嘗試，但失敗鏈補上：`json.loads` →（既有 fence/brace）→ **`json_repair.loads`** →（全失敗）**`_strip_fences`**（剝掉 ```json/``` 與外殼，**絕不回傳含 `{"answer"` 的原文**）。`json_repair` 與 `_strip_fences` 已存在，接進 `parse_qa_response` 的 fallback 即可。

**A2 — `stream_answer` 串流防漏（token 時）**
維持「prose-then-fence」常態（串 ``` 之前的乾淨 prose、遇 ``` 截斷）。**新增 JSON-first 守門**：若累積文字在出現任何 prose 前就以 `{` / `{"answer"` 開頭（模型沒寫 prose 直接吐 JSON），**不串 raw**，改用 `_partial_answer`（`json_repair` 增量解出當前 `answer` 欄位值）只串乾淨增量。`_partial_answer` 已存在（stash 中，實作時取回）。

**結果**：串流中與最終畫面**都不會出現 JSON 結構**，即使模型吐歪。

## 四、Part B — 平滑串流打字機（前端 `app.js` + `progressive-md.js`）

**B1 — token 改餵定速緩衝**
`/qa/stream` 的 `token` 事件目前直接丟給 `createProgressiveRenderer`（拿 chunk 即渲染 → 一坨一坨跳）。改為**餵進 `createTypewriter`**（既有：定速逐字、CJK 友善、buffer 解耦到達/顯示），即 `tw.push(d.text)`。Gemini 一坨吐進 buffer、打字機平穩放出 → **不管 chunk 多不均都平滑**（即 Vercel `smoothStream` 模式）。

**B2 — 每 tick 渲染 healed markdown**
`createTypewriter` 的 live 尾端已用 `stripInProgressTable`（藏進行中表格）；commit 區塊走 `mdToHtml`。確保 live 渲染走 `safeMarkdownPrefix`（藏半截表格/未閉合粗體）→ **表格收尾才 snap-in、不露 raw `|`、不頻閃**。

**B3 — backlog 自適應節奏（避免落後生成太多）**
固定 34 cps 在長答案會讓「顯示」遠落後「生成」。新增：當 buffer backlog 大（例如 > N 字）時**動態加速** cps（追上生成）、backlog 小時回正常節奏；設上限避免快到失去打字感。預設區間約 34–120 cps。

**B4 — 收斂單一渲染器**
串流與 replay/fallback 都改用 `createTypewriter` → 移除串流專用的 `createProgressiveRenderer` 路徑（少維護一套）。

## 五、Part C — 模式與回退（`backend/main.py`）

- `QA_MODE=stream`（**預設**）：2.5 串流強化 + 平滑打字機（本設計）。
- `QA_MODE=replay`：3.5 非串流結構化（從 stash 取回，當未來選項；非預設）。
- 兩個 env 開關（`QA_MODE`、`GEMINI_QA_MODEL`）成套切；master 不動；分支 `feat/qa-hardening-smooth-stream`。

## 六、錯誤處理

- 串流/解析任何例外 → 既有 error 事件 → 前端紅字提示；解析永遠走「絕不漏鷹架」fallback。
- 429/503：沿用既有 client 退避重試（注意：embedding 429 多為本機爆量測試造成，production 正常；retry 不過度放大留待 plan 評估是否微調）。

## 七、測試策略（TDD，先紅後綠）

- **單元（pytest）**：`parse_qa_response` 強化（壞 JSON / JSON-first / 截斷 → json_repair 救回；全壞 → `_strip_fences` 不漏鷹架）；`_partial_answer` 增量抽取；`stream_answer` JSON-first 守門（mock 串流吐 raw JSON → 不漏 `{"answer"`）。
- **單元（前端 .mjs）**：`createTypewriter` 定速+backlog 加速、`stripInProgressTable`（已測）、healed live 尾端不露 raw `|`。

# Q&A 改版設計：3.5-flash 結構化輸出 + 打字機回歸

> 設計日期：2026-06-05（Session 5）
> 範圍：**僅 `/qa` 問答**。不動 `/recommend`、不刪舊串流路徑、不加 code-fence 防呆（皆另議/YAGNI）。

## 一、問題與動機

**症狀**：問答回應仍會把 JSON schema（`{"answer": ...}` / ```json 鷹架）外洩到畫面，偏好發於 mobile。

**根因（已追蹤確認）**：現行 `/qa/stream` 用 `gemini-2.5-flash` 自由文字 + file_search，被迫把「含表格/換行的多行 Markdown」塞進 JSON 字串欄位再從文字硬解。JSON 規範字串內不能有字面換行，模型在高負載（mobile 網路差 → 易撞 429/high-demand）下常吐非法 JSON → `parse_qa_response` 兩條解析路都失敗 → fallback `return {"answer": stripped}` 把含鷹架的原文整包當答案顯示。

**第二需求**：上次為修「圖表漸進渲染」把串流路徑的打字機效果拿掉（改 `createProgressiveRenderer`），使用者想要回文字打字機，同時保留表格正確 snap-in。

## 二、關鍵實測證據（probe，唯讀，打既有 store）

| 組合 | 結果 |
|---|---|
| **非串流 3.5 + file_search + response_schema**（thinking 預設） | ✅ 完整 JSON、`\n` 正確跳脫、無 ``` 鷹架、**grounding 6 筆 course_id**、`json.loads` 穩過 |
| 非串流 3.5 + 上述 + **顯式 thinking_config** | 🔴 截斷、`json.loads` 失敗、**grounding 0 筆** |
| 2.5 + file_search + response_schema（對照） | ❌ `400: Tool use with response mime type 'application/json' is unsupported` |
| **串流** 3.5 + schema + file_search（×3 次） | 文字逐塊增量 ✅；但首 text 15~38s、**grounding 3 次都 0 筆**、長答案會截斷成非法 JSON 🔴 |

**結論**：
1. 2.5-flash 根本不准 file_search + JSON 結構化輸出（確認舊架構為何被迫硬解）。
2. **非串流 3.5 + response_schema 完美**：valid JSON、真結構化 grounding、不漏。
3. 3.5 **串流**反而脆弱（掉 grounding、會截斷）→ 不走串流。
4. 雷：**勿設顯式 `thinking_config`**（預設 thinking 即可）。

## 三、選定方案：A — 非串流結構化 + 前端打字機重播

後端一次 `generate_content`（3.5 + schema）回完整乾淨資料 → 前端用既有 `createTypewriter` 重播逐字 + 表格 snap-in。

**取捨（已與使用者確認接受）**：放棄「邊生成邊吐字」的 live 感；使用者看 stage loader 等生成（~30-45s）後才開始打字。換得最 robust（不漏 JSON、citations 是真的、不截斷）、最大重用既有碼。

## 四、架構與資料流

```
使用者問題 → 前端 askQuestion()（EventSource GET /qa/stream）
  → 後端 /qa/stream（QA_MODE=replay）：
      ① 立即送 stage 事件（觸發 firstEvent、防誤觸 fallback）
      ② await answer_question_structured()
      ③ 三層解析：response.parsed → json.loads → json_repair
      ④ 結構化 grounding course_ids → extract_citations
         （空 → extract_citations_by_name；真查無 → 防幻覺覆寫）
      ⑤ 送單一 done：{answer, citations, followups, session_id, turn_number}
  → 前端 done：createTypewriter 重播 answer（逐字 + 表格 snap-in）→ 掛 citations/followups
```

**不漏 JSON 的保證**：`answer` 是後端從結構化物件取出的純 markdown 字串，前端全程只碰 markdown，JSON 永不進前端。

## 五、後端設計（`backend/qa.py` / `backend/main.py` / `requirements.txt`）

**Schema 常數**
```python
_QA_RESPONSE_SCHEMA = {
  "type": "object",
  "properties": {
    "answer": {"type": "string"},
    "followup_suggestions": {"type": "array", "items": {"type": "string"}},
  },
  "required": ["answer", "followup_suggestions"],
}
```

**新函式 `answer_question_structured(client, store, question, history)`（非串流）**
- `client.models.generate_content(model=GEMINI_QA_MODEL, contents=build_qa_contents(question, history), config=cfg)`
- `cfg = GenerateContentConfig(system_instruction=_SYSTEM_INSTRUCTION, temperature=0.2, top_p=0.95, max_output_tokens=8192, response_mime_type="application/json", response_schema=_QA_RESPONSE_SCHEMA, tools=[file_search(store)])`
- **無顯式 `thinking_config`**（Probe B：三開會截斷/掉 grounding）。
- **`max_output_tokens=8192`**：thinking 會吃輸出預算，2048 在長答案會截斷。
- 回 `{answer, followup_suggestions, citations_course_ids, latency_ms}`。

**三層解析保險**：`response.parsed`（Probe A 回 dict）→ `json.loads(response.text)` → `json_repair.loads(text)`；全失敗才退「整段當 answer 但先剝 ```fence」（絕不漏鷹架）。`requirements.txt` 加 `json-repair`。

**System instruction 瘦身（`_SYSTEM_INSTRUCTION` / `_PROMPT_TEMPLATE`）**
- **保留**：首段「【鐵則・最高優先】先檢索」（grounding 命脈）、主題邊界、`answer` 內容的 markdown 格式指引（表格欄位固定「課程名稱 | 系所 | 重點」、克制粗體）。
- **移除**：「另外輸出 ```json 區塊」「嚴禁說明文字輸出 JSON」等 JSON 包裝指示；`_PROMPT_TEMPLATE` 的 JSON 尾巴。
- **註**：Probe A 用精簡 system instruction + schema 仍拿到 6 筆 grounding → CLAUDE.md #15「拿掉 JSON 包裝破壞 grounding」是 **2.5 自由文字**才有的問題，**3.5+schema 不適用**。

**Grounding 萃取**：非串流 response 走 `candidates[].grounding_metadata.grounding_chunks[].retrieved_context` → 重用既有 `_course_id_from_retrieved_context`。citations 空 → `extract_citations_by_name`（既有）→ 真查無 → `should_override_no_results` 防幻覺覆寫（既有，全沿用）。

**`main.py`：`QA_MODE` 切換整個 QA 堆疊（兩端點一致，避免半套狀態）**
- `QA_MODE=replay`（預設，新）：
  - `/qa/stream`：送 stage 事件 → `await answer_question_structured()` → 送單一 `done`。
  - `POST /qa`：呼叫 `answer_question_structured`（fallback 也享 3.5+schema）。
- `QA_MODE=stream`（舊，回退）：
  - `/qa/stream`：走現有 `stream_answer`（2.5 自由文字串流）。
  - `POST /qa`：走現有 `answer_question`（interactions, 2.5）。
- 持久化（insert_turn/bump_session）兩模式皆沿用。
- ⚠️ **一致性**：`GEMINI_QA_MODEL` 只在 `replay` 模式生效且必須是 3-series（2.5 配 schema 會 400）；`stream` 模式維持現行硬寫的 2.5。兩個 env 要成套切（replay+3.5 或 stream+2.5），不可交叉。

## 六、前端設計（最小手術，`app.js` + `progressive-md.js`）

**做法**：不重寫合併。**重用既有 `createTypewriter`** 當重播器（fallback 已在用、已驗證），只加一個小修正。

- `done` handler（`app.js:969`）：收到完整 `data.answer` → `createTypewriter` 重播（逐字）→ 完成後 `attachCitesAndFollowups`。client-side stage loader 在生成期間照跑。
- **小修正**：`createTypewriter` 的 live 尾端若是「進行中的表格」（以 `|` 起頭、未以 `\n\n` 收尾）→ **先藏**，不露 raw `| |`。表格收尾才 snap-in 成格式化 HTML（沿用現有 committed-block 機制）。
- guard：非串流首 `done` 可能 ~30-45s。靠後端立即 stage 事件先觸發 `firstEvent` 防誤觸 fallback；必要時放寬 replay 模式 guard。

**明確不做**：合併重寫兩個渲染器、code-fence 防呆（皆排入未來清理/YAGNI）。

## 七、錯誤處理與回退

**錯誤**：3.5 呼叫失敗（503/429）沿用既有 `retry_options` 指數退避；最終失敗 → 既有 error 事件 → 前端紅字。解析三層保險 + 「絕不漏鷹架」。

**回退（三層）**：
1. 新分支開發，master 不動 → `git checkout master` 即回現狀。
2. 並存 + env 開關：`QA_MODE=replay|stream`、`GEMINI_QA_MODEL=gemini-3.5-flash|gemini-2.5-flash` → 不動 code 即切回。
3. 部署層：`git revert` merge / 重部署 master。
